1.3 Helper لمفتاح عدم التكرار (Idempotency)
القواعد من Controller::idempotencyKey:

طول المفتاح من 1 لـ 128 حرف، وغير كده الطلب بيترفض.
لو نفس المفتاح اتبعت مع بيانات مختلفة بيرجع 409.
production-receipts بيرفض الطلب لو مفيش مفتاح (422).
انسخ نفس النمط اللي في manufacturing-pages.jsx بالظبط واعمله hook مشترك اسمه useIdempotencyKey:

Copyconst ref = useRef(null);
function keyFor(payload) {
  const hash = JSON.stringify(payload);
  if (!ref.current || ref.current.hash !== hash) ref.current = { hash, key: crypto.randomUUID() };
  return ref.current.key;
}
function reset() { ref.current = null; } // تتنادى بعد النجاح بس
قاعدة ذهبية: متولدش مفتاح جديد لما المستخدم يعيد المحاولة على نفس البيانات. المفتاح الجديد بيتولد بس لو البيانات اتغيرت أو العملية نجحت.

استخدم normalizeError الموجودة في catalog/errors.ts، وهي بترجع { status, message, fields, summary }. اتعامل مع كل status كده:

Status	التصرف في الواجهة

2.2 إنشاء وتعديل فرع
Create: POST branches: { name*, code*, type* ('branch'|'warehouse'), phone?, email?, address?, city?, city_id?, is_active? }
code بيتحول uppercase وفريد على مستوى السيستم كله، وطوله max 50. وemail بيتحول lowercase.
المدينة اختيارية في الـ backend. لو التصميم معلّمها كإجبارية، شيل النجمة أو سيبها required في الواجهة بس بقرار واضح. حط maxLength=100 لأن الـ Update بيسمح بـ 100 بس والـ Store بيسمح بـ 120.

تفعيل وتعطيل: PUT branches/{id} مع { is_active: false }.

المصدر: GET production-receipts/options?search=.... بيرجع variants: [{ id, label: "اسم المنتج بالعربي / SKU" }]، بحد أقصى 50 نتيجة، وللمتغيرات النشطة بس، ومحتاج صلاحية inventory.view.
اعمل debounce بـ 300ms. ولو البحث فاضي اعرض "اكتب للبحث"، متعرضش أول 50 على إنهم كل المتغيرات.
البحث بيشتغل على SKU والباركود والاسم العربي والإنجليزي.
المتغيرات المعطلة: مش هتظهر في الـ picker. ده مقبول في الإدخال (الـ backend بيرفض الإدخال على متغير معطل أصلًا). لكن لو محتاج تعمل decrease لمتغير معطل لتصفية رصيده، المستخدم يفتح شاشة الأرصدة، ومنها زرار "تسوية" يمرر variantId في الـ hash.
كاش الأسماء: اعمل variantCache (Map) في الـ context، وكل ما توصلك بيانات متغير من أي مصدر (options، أو StockLevel.variant اللي فيه product_name_ar/en) خزّنها فيه. الشاشات اللي بيرجعلها SKU بس (الحركات والتحويلات والجرد) تعرض الاسم من الكاش لو موجود، ولو مش موجود تعرض SKU بس. متعملش request لكل صف.
المرحلة 4: أرصدة المخزون (stock)
GET inventory بالفلاتر دي: branch_id, location_id, product_id, product_variant_id, low_stock (boolean: ابعت 1/0)، وper_page (max 100). وبيرجع pagination عادي.
مفيش بحث نصي. فلتر الصنف يتعمل بالـ VariantPicker اللي بيبعت product_variant_id.
الأعمدة: المنتج (pickName)، والـ SKU، والفرع، والموقع (location.name أو "بدون موقع")، والموجود on_hand، والمحجوز reserved، والتالف damaged، وقيد النقل in_transit، والمتاح available (متحسبوش في الواجهة، خده من السيرفر)، وحد إعادة الطلب reorder_level، وآخر تحديث updated_at.
is_low_stock بيحدد شكل الصف أو الـ badge "منخفض".
الـ KPIs: لو التصميم فيه "إجمالي المتاح" على كل المخزون، فده مش متاح من الـ API لأن الـ endpoint بيرجع صفحة واحدة. يا إما تكتب جنبه "في الصفحة الحالية"، يا إما تشيله لحد ما يتعمل endpoint ملخص. القرار يتوثق في الكود.
الفلاتر تتحفظ في الـ hash query عشان deep-linking.
المرحلة 5: سجل الحركات (moves)
GET inventory/movements بالفلاتر دي: branch_id, location_id, product_id, product_variant_id, type, from_date, to_date (بصيغة YYYY-MM-DD، وto_date لازم تكون أكبر من أو تساوي from_date)، وper_page.
Cursor pagination: الرد فيه meta.next_cursor وmeta.prev_cursor. اعمل زرارين "السابق" و"التالي" بيبعتوا cursor=<القيمة>. مفيش أرقام صفحات ولا total. شيل أي "صفحة 3 من 10" من التصميم.
لما أي فلتر يتغير، امسح الـ cursor وارجع لأول صفحة.
عمود التكلفة unit_cost يظهر بس لو can('inventory.view_cost'). والـ backend أصلًا مش بيبعته من غير الصلاحية.
الشاشة للعرض بس، مفيش أي زرار تعديل.
النوع بيتعرض من MOVE_TYPE_LABELS. ولو جه نوع مش موجود في الـ mapping اعرض القيمة الخام في badge رمادي، والصفحة متقعش.
الكمية: موجب أخضر وسالب أحمر، وbalance_before يليه balance_after.
المرحلة 6: التسويات (adjust)
Payload: POST inventory/adjustments مع Idempotency-Key:

Copy{
  "branch_id": 1,
  "location_id": 5,
  "items": [
    { "product_variant_id": 12, "adjustment_type": "increase", "quantity": 10, "reason": "رصيد افتتاحي" }
  ]
}
location_id اختياري، ولازم يكون تابع للفرع.
items من 1 لـ 100. والكمية أكبر من صفر وبحد أقصى 4 خانات عشرية. وreason max 1000 حرف.
الأنواع: استخدم ADJ_MOCK_TO_API. متبعتش dmg_mark وما شابه.
كل البنود في transaction واحدة: لو بند واحد فشل، كله بيترجع.
الرد بيكون 201 ومعاه { message, data: StockMovement[] }.
الأخطاء:

نقص رصيد: BusinessException برسائل زي "الرصيد غير كافٍ في (on_hand)…" أو "الكمية المتاحة للبيع (x) غير كافية…". اعرضها فوق الفورم.
"المخزون مشغول بعملية أخرى…": اعرض زرار إعادة محاولة بنفس المفتاح.
422 على بند: الصف يتلون والرسالة تظهر تحته.
بعد النجاح: reset() للمفتاح، وتفضّي الفورم، وtoast، واختياري تروح للحركات مفلترة بالفرع.

التحقق: جرّب الخمس أنواع. واعمل decrease أكبر من الرصيد (لازم يترفض). واعمل double-click على زرار التنفيذ (لازم تتسجل حركة واحدة بس، وده بيحصل عن طريق busy والمفتاح الثابت).

المرحلة 7: التحويلات (transfers, transfer, transfer-edit)
7.1 القائمة
GET transfers بالفلاتر دي: from_branch_id, to_branch_id, status, per_page. والـ badge من TRANSFER_STATUS.

7.2 إنشاء وتعديل مسودة
Create: POST transfers مع Idempotency-Key:
Copy{ "from_branch_id": 1, "to_branch_id": 2, "notes": "...",
  "items": [ { "product_variant_id": 12, "from_location_id": 5, "to_location_id": 9, "requested_qty": 8 } ] }
الفرعين لازم يكونوا مختلفين ونشطين. ومواقع المصدر لازم تبقى من فرع المصدر، ومواقع الوجهة من فرع الوجهة (لو المستخدم غيّر الفرع، صفّر المواقع المختارة). البنود من 1 لـ 100.

Update: PUT transfers/{id} بنفس الحقول (sometimes). افتح TransferService::update واتأكد إن items بتعمل replace كامل وإن التعديل مسموح في draft بس. زرار التعديل يظهر بس لما status === 'draft' والمستخدم عنده transfers.update.
Delete: DELETE transfers/{id} للمسودة بس.
7.3 دورة الحياة (شاشة التفاصيل)
المرحلة	الزرار يظهر لما	الطلب	الأثر على المخزون
اعتماد	draft + transfers.approve	POST transfers/{id}/approve	الكمية بتتنقل من on_hand لـ reserved في المصدر
شحن	approved + transfers.ship	POST .../ship	من reserved لـ in_transit
استلام	shipped + transfers.receive	POST .../receive	بتدخل on_hand في الوجهة، والفرق بيتسجل transfer_shortage
إلغاء	حسب الـ service + transfers.update	POST .../cancel	بيفك الحجز أو قيد النقل حسب المرحلة
Payload الاعتماد والشحن والاستلام (مهم):

Copy{ "expected_version": 3,
  "items": [ { "id": 101, "approved_qty": 8 } ] }
items.*.id هو id بند التحويل (StockTransferItem.id)، مش product_variant_id. ده أكتر غلط متوقع.
اسم حقل الكمية بيختلف حسب المرحلة: approved_qty في الاعتماد، وshipped_qty في الشحن، وreceived_qty في الاستلام. والكمية من 0 وطالع، وبحد أقصى 4 خانات عشرية.
items اختياري. البند اللي مش موجود بياخد كمية المرحلة اللي قبلها كقيمة افتراضية. الأسهل إنك تبعت كل البنود دايمًا والقيمة الافتراضية متعبية في الـ input.
ابعت expected_version دايمًا من transfer.version اللي اتحمّل. لو حد تاني عدّل التحويل، السيرفر بيرجع تعارض برسالة "تم تعديل التحويل؛ أعد تحميله وراجع الكميات." ساعتها اعرض الـ banner وزرار إعادة تحميل، ومتعيدش الإرسال أوتوماتيك.
في الاستلام اعرض عمود "العجز" = shipped - received وهو محسوب في الواجهة للعرض بس، وقبل التأكيد اعرض تحذير لو فيه عجز.
الإلغاء: POST .../cancel من غير body. افتح TransferService::cancel وحدد المراحل المسموح فيها (المتوقع draft وapproved، ومش shipped). اعرض الزرار في المراحل دي بس. وبعد الإلغاء اعمل reload، متغيرش الـ badge محليًا.

بعد كل عملية ناجحة، الـ resource الراجع فيه النسخة الجديدة والـ version الجديد. حدّث الشاشة بيه أو اعمل reload.

أسماء المنتجات: البنود فيها sku بس، فاستخدم variantCache.

المرحلة 8: الجرد (counts, count)
8.1 القائمة
GET stocktakes بالفلاتر دي: branch_id, status, per_page. والحالات: draft, in_progress, approved, cancelled.

8.2 الإنشاء
POST stocktakes مع Idempotency-Key:

Copy{ "branch_id": 1, "location_id": null, "notes": "...",
  "items": [ { "product_variant_id": 12, "counted_qty": null } ] }
مهم: لو بعت من غير items، الـ backend مش بياخد snapshot لكل الرصيد. يعني لو التصميم فيه "جرد شامل للفرع أو الموقع"، الواجهة هي اللي تعمل كده:
تجيب كل الأرصدة: GET inventory?branch_id&location_id وتلف على الصفحات.
تجمع product_variant_id مميزة (distinct).
تبعت أول 500 في POST، وتبعت الباقي على دفعات كل دفعة 500 عن طريق PATCH stocktakes/{id}/items.
system_qty بيتسجل كـ snapshot من on_hand لحظة إضافة البند.
الجرد بيتنشئ بحالة draft.
8.3 العدّ والحفظ
بدء العد: PUT stocktakes/{id} مع { "status": "in_progress" }. وفيه انتقال تاني مسموح من draft وهو cancelled.
حفظ الكميات: PATCH stocktakes/{id}/items:
Copy{ "items": [ { "product_variant_id": 12, "counted_qty": 7 }, { "product_variant_id": 13, "counted_qty": 0 } ] }
ده upsert جزئي: البنود اللي مش متبعتة مش بتتمسح. والحد 500 بند في الطلب، فقسّم لو أكتر.

التمييز بين "لم يُعد" و"صفر" (مطلوب صريح في الـ handoff):
الـ input الفاضي معناه null، وده "لم يُعد" ويظهر بـ badge رمادي.
0 معناه "صفر فعلي".
ممنوع أي Number('') أو || 0 يحوّل الفاضي لصفر. اكتبها صريحة: v === '' ? null : Number(toLatinDigits(v)).
اعرض الفرق difference اللي راجع من السيرفر بعد الحفظ.
احفظ بس البنود اللي اتغيرت (dirty) عشان تقلل حجم الطلب، واعرض "تغييرات غير محفوظة" لو المستخدم حاول يخرج.
8.4 الاعتماد
POST stocktakes/{id}/approve من غير body. سياسة البيانات القديمة (stale) بتتحدد من config السيرفر.
افتح StocktakeService::approve واعرف هل الاعتماد مسموح من draft ولا لازم in_progress، وأظهر الزرار على الأساس ده.
الرفض المتوقع:
"لا يمكن اعتماد جرد بلا عناصر."
"لا يمكن الاعتماد: توجد عناصر لم تُعدّ بعد." ساعتها اعمل highlight على البنود اللي counted_qty === null.
"العد الفعلي أقل من المحجوز والتالف…".
بيانات قديمة: "توجد أصناف تغيّر رصيدها بعد عدّها…" ومعاها recount_item_ids وrecount_variant_ids. علّم البنود دي بـ "تحتاج إعادة عدّ"، وزرار "إعادة العد" يبعت PATCH items مع { product_variant_id, recount: true, counted_qty: <الجديدة> }. مكان البيانات دي في الـ JSON بيتحدد حسب اللي هتلاقيه في المرحلة 1.4.
بعد الاعتماد، الجرد بيبقى read-only بالكامل.
