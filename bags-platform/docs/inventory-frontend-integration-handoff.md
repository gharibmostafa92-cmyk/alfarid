# تسليم ربط واجهات المخزون بالـ backend

## نطاق المهمة

ربط الشاشات الثمانية الموجودة في `frontend/apps/backoffice/src/pages/admin/inventory-mock/` بالـ API الحقيقي، مع الحفاظ على تصميم `bags-platform/exuction.txt` وVortix وRTL:

1. الفروع والمخازن: قائمة، إنشاء، تعديل، تفعيل/تعطيل، حذف مع عرض سبب الرفض.
2. مواقع التخزين داخل الفرع: رف، منطقة، خانة، تالف، استلام؛ كود فريد داخل الفرع.
3. أرصدة المخزون: فلترة بالفرع والموقع والمنتج والمتغير والمنخفض؛ الموجود والمحجوز والتالف وقيد النقل والمتاح وحد إعادة الطلب وآخر تحديث.
4. التسويات: زيادة، نقصان، تسجيل تالف، إعدام تالف، استرجاع من التالف؛ فرع وموقع اختياري، حتى 100 بند وكميات موجبة حتى 4 منازل عشرية.
5. الحركات: سجل للعرض فقط، فلاتر المكان والصنف والنوع والتاريخ، تكلفة حسب الصلاحية، السابق/التالي بالمؤشر.
6. التحويلات: مسودة، اعتماد، شحن، استلام، إلغاء؛ الكميات المطلوبة والمعتمدة والمشحونة والمستلمة ومواقع المصدر والوجهة.
7. الجرد: إنشاء، عدّ، حفظ، اعتماد؛ حتى 500 بند في طلب الإنشاء؛ التمييز بين غير معدود وكمية صفر.
8. استلام الإنتاج: رقم الدفعة، الفرع، الموقع، الملاحظات؛ حتى 50 متغيراً بكمية صحيحة وتكلفة وحدة، مع الصلاحيات اللازمة.

لا تشمل المهمة شاشات الكاشير أو المشتريات أو العملاء أو الشحن أو ربط الذكاء الاصطناعي. بعض الملفات المشتركة مثل routes/api/admin.php وapi-client تحتوي تعريفات لهذه الأجزاء؛ وجودها لا يوسع نطاق المهمة.

## نقطة الدخول الحالية

- `App.tsx` يعرض InventoryMockPage داخل FinancialDashboard باستخدام lazy/Suspense.
- رابط البداية: `/dashboard#/inventory/stock`.
- مسارات الشاشات: branches, locations, stock, adjust, moves, transfers, transfer, transfer-edit, counts, count, production.
- معاملات مثل branchId وid وvariantId موجودة في query داخل hash. المعرّفات الحالية النصية مثل b1/v1/t1 تجريبية؛ الـ API يستخدم معرفات رقمية.
- InventoryMockPage يعزل CSS داخل Shadow DOM ويتبع حدث مظهر Vortix. inventory-reference.jsx يجمع الشاشات والنماذج والـ mock حالياً.
- تغييرات mock في ذاكرة الواجهة، وليست كتابة على قاعدة البيانات. إزالة هذه المحاكاة جزء من مرحلة الربط القادمة.
- ملف المصدر يضم shell تجريبياً؛ لا تعيد إنشاء shell ثانٍ. الهيدر والـ sidebar الحاليان في Vortix هما المعتمدان.
- توجد شاشة استلام إنتاج متصلة بالفعل في `catalog/manufacturing-pages.jsx` وendpoints مشتركة؛ راجعها كمرجع قبل إنشاء تكامل مكرر. لا تكسر المسار الحالي `/production`.

## خريطة API

الأساس `/api/v1/admin`؛ راجع Controllers وRequests وResources المرفقة باعتبارها المصدر النهائي للعقد.

| الشاشة | المسارات |
| --- | --- |
| الفروع | GET/POST branches، GET/PUT/DELETE branches/{branch} |
| المواقع | GET/POST branches/{branch}/locations، GET/PUT/DELETE branches/{branch}/locations/{location} |
| الأرصدة | GET inventory |
| التسويات | POST inventory/adjustments |
| الحركات | GET inventory/movements |
| التحويلات | transfers CRUD، POST transfers/{transfer}/approve أو ship أو receive أو cancel |
| الجرد | stocktakes CRUD، PATCH stocktakes/{stocktake}/items، POST stocktakes/{stocktake}/approve |
| استلام الإنتاج | GET production-receipts/options، GET/POST production-receipts |

## نقاط لا يصح افتراضها من التصميم

- المخزن نوع `warehouse` من Branch، وليس كياناً مستقلاً. نموذج الفرع له name واحد. لا يوجد حقل «مخزن افتراضي» في نموذج الإنشاء الحالي.
- منتج الكتالوج ومتغيره منفصلان عن رصيد المخزون. كل بند مخزني ينتهي إلى product_variant_id؛ لا تختَر المنتج فقط.
- تحديث الرصيد حصراً من خدمات المخزون، وليس عبر تعديل أرقام جدول الأرصدة مباشرة.
- الرصيد الافتتاحي يمكن تسجيله كتسوية increase مع سبب واضح؛ لا تفترض endpoint جديداً.
- أسماء أنواع التسويات في mock مختلفة عن API؛ مثال dmg_mark في mock مقابل mark_damaged في StoreAdjustmentRequest. اعمل mapper صريحاً.
- حالة الجرد counting في mock تقابل in_progress في backend. افحص الـ enums ولا ترسل نص mock كما هو.
- شاشة الحركات تستخدم cursor pagination، بينما قوائم أخرى تستخدم pagination عادية. استلام الإنتاج يرجع paginator مباشرة، وبعض القوائم ResourceCollection تحت meta؛ لا توحّدها بافتراض خاطئ.
- Branches/Locations لا يدعمان جميع فلاتر mock نفسها؛ افحص index في Controller. أي فلتر غير متاح يحتاج قرار تنفيذ واضح، لا تعرضه كبحث شامل بينما يبحث في صفحة واحدة فقط.
- اقرأ BranchAccess قبل عرض فروع المستخدم وتنفيذ العمليات. صلاحيات تكلفة المخزون inventory.view_cost مختلفة عن products.view_cost التي تستخدمها تكلفة الإنتاج.
- ProductionReceipt يتطلب Idempotency-Key. راجع Controller الأساسي والخدمات لمنع تكرار التسويات والإنشاء عند إعادة المحاولة؛ لا تولّد مفتاحاً جديداً لكل retry لنفس العملية.
- التحويلات والجرد يدعمان فحوص التزامن؛ راجع expected_version وexpected_updated_at حيث يقبلهما الطلب والخدمة.
- إلغاء تحويل له شرط مراحل وآثار على الحجز وقيد النقل. لا تحاكي تغيير badge فقط عند الربط.
- تحقق من المدينة المطلوبة في mock مقابل قواعد الفرع الفعلية، ومن قيود التعطيل والحذف وأسباب HTTP 409/422.
- خيارات الإنتاج محدودة بنتائج البحث؛ ليست قائمة شاملة لكل المتغيرات. لا تعتمد عليها دون بحث/تحميل مناسب لكل احتياج.
- احتفظ برسائل الخادم وأخطاء الحقول، وحالات التحميل والفراغ والخطأ وإعادة المحاولة و403 و404 والتعارض.

## التحقق المطلوب عند تنفيذ الربط

- حالات الصلاحيات المختلفة والعرض فقط وتقييد الفرع.
- CRUD للفروع والمواقع، وحذف مرفوض بسبب الارتباطات.
- اختيار SKU حقيقي، وفلاتر الأرصدة، وتنقل الحركات بالمؤشر.
- أنواع التسويات الخمسة ومنع نقص الرصيد وإعادة المحاولة بلا تكرار.
- دورة التحويل كاملة، وتعارض التحديث، والإلغاء حسب المرحلة.
- جرد بصفر فعلي وبنود لم تعدّ، والحفظ والاعتماد وحساب الفرق.
- استلام الإنتاج والتكلفة والفرع والموقع وعدم تكرار الاستلام.
- الحفاظ على الشكل وRTL والوضعين الفاتح والداكن وعلى تسجيل الدخول والصفحات الحالية.

الاختبار `inventory-mock.e2e.cjs` يثبت عمل التصميم الحالي بدون API؛ يجب تحويله أو إضافة اختبارات تكامل عند تنفيذ الربط. اختبارات backend المرفقة توضح قواعد الأعمال وحالات الرفض والتزامن.
