# مراجعة تحسينات الكتالوج

تاريخ المراجعة: 15 أكتوبر 2026.

تمت مراجعة الملاحظات H1–H4 وM1–M11 وL1–L9 على الكود الحالي، وليس على ملف Repomix القديم. عند بدء المراجعة كان هناك 133 اختبارًا: نجح 125 وفشل 8. ستة إخفاقات كانت مشاكل فعلية، واثنان كانا توقعين قديمين لا يتفقان مع التغييرات المقصودة: السماح بـSVG، وقبول per_page سالب.

## المشاكل التي أُصلحت في هذه المراجعة

- أُعيد منع حقول id وproduct_id وغيرها داخل variants المتداخلة، والتحقق من SKU وbarcode المكرر داخل الطلب نفسه قبل الكتابة.
- أُعيد تجاهل سعر التكلفة في إنشاء المنتج بمتغيراته إذا لم يملك الموظف products.view_cost.
- أُصلح slug الفارغ عند تحديث المنتج حتى لا يصطدم بعمود NOT NULL.
- أُعيد جمع كتابة القسم/البراند وصورتهما في transaction واحدة. نقل عمليات الملفات خارج transaction كان يسمح بحفظ بيانات جزئية رغم فشل الرفع.
- أُضيف TransactionalMediaObserver: تنظيف كل الملفات والتحويلات الجديدة بعد rollback، بما فيها الصورة التي فشلت أثناء التحويل؛ وتأجيل مسح الملفات الموجودة حتى afterCommit. اختُبرت أيضًا rollback لعملية خارجية تحتوي استبدال شعار أو حذف صورة.
- عمليات رفع/ترتيب/حذف الميديا تقفل صف المنتج وتقرأ الحالة الحالية؛ حماية آخر صورة لا تعتمد على نسخة قديمة من الموديل أو مجموعة صور سبق تحميلها.
- changeStatus أصبحت تفتح transaction بنفسها، وتقرأ المنتج الحالي قبل قفل قسمه، بدل الاعتماد على وجود transaction عند كل مستدعٍ.
- أُضيف قفل advisory مشترك لعمليات إنشاء/تعديل/نشر المنتجات، يقابله قفل حصري لتعديلات الأقسام على المفتاح نفسه. يمنع هذا سباق نشر المنتج أو نقله مع تعطيل القسم/أحد أسلافه، دون تسلسل تعديلات المنتجات المختلفة كلها على قفل حصري واحد.
- إنشاء المنتج وإسناد قسم/براند جديد يتأكدان من وجود الصف غير المحذوف بعد انتظار القفل، بدل تجاهل نتيجة first() الفارغة. تحديث المتغير يعيد قراءته بعد قفل المنتج حتى لا يفحص التركيبة باستخدام بيانات قديمة.
- قواعد color_name_en تعمل داخل variants.* على العنصر نفسه. التعديل الجزئي يحتفظ بالاسم الإنجليزي الحالي، ويرفض تفريغه عند بقاء الاسم العربي أو hex.
- فلاتر الأقسام تُفحص قبل فرع tree. parent_id[]=1 وtree[]=1 لم يعودا يتجاوزان الفحص أو يتسببان في تحويل array إلى string. المعرّفات الطويلة خارج نطاق قاعدة البيانات تُرفض في المسار بـ404.
- أُعيد رفض الأقسام/المتغيرات المحذوفة في ترتيب الأقسام ورفع صور المتغير، ومنع IDs المكررة في ترتيب الأقسام.
- حدود المصفوفات تُفحص في prepareForValidation قبل توسيع wildcard rules وتشغيل استعلامات كل عنصر؛ مجرد max على المصفوفة لا يوقف Laravel عن فحص جميع عناصر طلب ضخم. يوجد اختبار يثبت عدم تنفيذ استعلامات product_variants للطلب الزائد عن 100 عنصر.
- مسارات UUID تحافظ على الوصول للملفات القديمة الموجودة تحت id، مع معالجة UUID الفارغ دون إرجاع مسار جذر القرص. اختُبر حذف الملفات القديمة وتحويلاتها دون مساس بملفات أخرى.
- أُصلح البحث عن النص "0" في قوائم الأقسام والبراندات والمنتجات، بدل اعتباره قيمة فارغة، وكذلك قبول اسم اللون النصي "0" في التعديل الجزئي.
- أُكمل eager loading لصور الأقسام والبراندات في show/store/update، وأُضيف id لترتيب الميديا المستقر.
- توليد slug يستخدم استعلامًا واحدًا ويختار أول لاحقة متاحة في الذاكرة، دون تحويل لاحقة يحددها المستخدم إلى integer قد يفيض.
- is_active=null في تعديل القسم يُعامل كعدم تغيير، بدل تشغيل فحص تعطيل القسم بالخطأ.
- تم تحديث توثيق API والاختبارات القديمة بخصوص منع SVG ورفض pagination غير صالحة.

## اختبارات التزامن

CatalogConcurrencyTest يشغّل عمليتي PHP منفصلتين واتصالين حقيقيين بقاعدة PostgreSQL. تقرأ العمليتان الموديلات أولًا، ثم تنطلقان من حاجز واحد. كل سيناريو ينتج نجاح عملية واحدة ورفض الأخرى بقاعدة بيزنس:

1. حذف آخر متغيرين نشطين: يظل متغير نشط واحد.
2. حذف آخر صورتين: تظل صورة واحدة وملفها على القرص.
3. نقل A تحت B وB تحت A: لا تتكون دورة.
4. نشر المنتج وتعطيل قسمه: لا توجد حالة نهائية فيها منتج منشور وقسمه غير نشط.

## التحقق النهائي

- php artisan test --compact: نجح 154 اختبارًا و735 assertion، بما فيها 21 اختبارًا جديدًا لهذه المراجعة.
- اختبارات السباقات الأربعة نجحت باستخدام عمليتي PHP واتصالين منفصلين بـPostgreSQL.
- Laravel Pint وcomposer validate وفحص git diff --check لملفات backend/docs المعدّلة: نجحت.
- مسارات المنتجات والأقسام موجودة؛ لا تغييرات على عناوين API المطلوبة.

تم تطبيق migrations المعلّقة بـphp artisan migrate --force على البيئة المحلية بعد التحقق أن APP_ENV=local. لم يتم استخدام migrate:fresh أو حذف بيانات قاعدة التطوير. لا توجد migrations معلّقة بعد ذلك.

## حدود وقرارات مقصودة

- المشروع ومحرك اختبارات التزامن الحاليان Laravel 13 وPostgreSQL. الأقفال الاستشارية مرتبطة بـPostgreSQL، وafterRollBack مستخدمة من الإصدار المثبّت فعليًا.
- UUID يقلل قابلية تخمين الروابط لكنه لا يجعل الملفات خاصة. الملفات القديمة لا تُنقل تلقائيًا ولا تُكسر روابطها. لم تُضف منظومة ملفات خاصة أو توقيع روابط إلى هذه المرحلة.
- منع SVG يمنع الرفع الجديد؛ لا يعيد كتابة محتويات ملفات SVG رُفعت سابقًا في أي بيئة أخرى.
- migration الفهارس الحالية مناسبة لبيئة التطوير. فهارس جداول إنتاج كبيرة تحتاج خطة نشر مستقلة بـCONCURRENTLY؛ لم يحدث اتصال ببيئة إنتاج.
- تبقى published_at الأصلية عند إعادة النشر، وتبقى سياسة آخر تعديل يفوز؛ لم تُضف optimistic locking غير مطلوبة بعقد API.
- تكلفة المتغير غير المرسلة تبقى 0 وفق مخطط المرحلة الحالي. فصل التكلفة المجهولة عن صفر يحتاج قرارًا لمرحلة المحاسبة/الهامش، ولم تُمنح صلاحية التكلفة لموظف غير مخوّل.
- لا توجد بيانات وصول إلى بيئة إنتاج للتحقق من APP_DEBUG فيها؛ التوثيق لا يعتبر قيمة .env.example دليلًا على إعداد نشر فعلي.
