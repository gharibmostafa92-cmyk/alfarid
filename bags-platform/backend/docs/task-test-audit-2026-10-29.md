# مراجعة اختبارات task.txt — 2026-10-29

تحديث سياسة التسجيل بطلب صاحب المشروع: إثبات ملكية الهاتف غير مطلوب افتراضيًا عند إنشاء حساب قطاعي أو جملة، وأُزيلت خطوة OTP من نموذج التسجيل. لا يُعلَّم الهاتف بأنه موثّق تلقائيًا. يلزم `CUSTOMER_REQUIRE_PHONE_VERIFICATION=false` وتحديث كاش الإعدادات عند ترقية بيئة سبق أن فعّلت الشرط. التحقق من مستندات تاجر الجملة مستقل عن إنشاء الحساب.

المراجعة شملت الاختبارات الموجودة وإضافات للحالات الناقصة، مع PostgreSQL 16 حقيقية واتصالات وعمليات PHP منفصلة لاختبارات التزامن. ملفات المشروع السابقة لم تُستبدل. الأرقام أدناه تخص هذه المراجعة، وليست نتائج التقارير القديمة.

## الإصلاحات المثبتة باختبارات فاشلة قبل الإصلاح

1. عناوين IPv4 بصيغة IPv6 كانت تتشارك دلو `/64` واحدًا. أصبحت تستخدم دلو IPv4 الأصلي، بما في ذلك حد شبكة checkout الإضافي. اختُبرت 16 عائلة من محددات الطلبات.
2. أخطاء HTTP والاتصال بمزود SMS كانت تخرج باستثناءات داخلية. أصبحت تعيد BusinessException بحالة 503 ورسالة عامة دون جسم رد المزود أو التوكن.
3. بناءً على اختيار صاحب المشروع: إشعار مرتبط بطلب سُدّد قبل المراجعة يُرفض مع توضيح السبب، قبل أي حركة خزينة. يُقفل الطلب ويُعاد فحص حالته داخل المعاملة.
4. بناءً على اختيار صاحب المشروع: المرجع المكرر لنفس التاجر يُرفض بـ409، مع تجاهل حالة الحروف والمسافات الطرفية. قفل صف العميل يمنع سباق الطلبات المرتبطة والحرة. تُحذف الملفات المحضرة للطلب المرفوض. المرجع نفسه مسموح لتاجر آخر. السجلات التاريخية الموجودة لا تُحذف ولا تُدمج تلقائيًا.
5. بحث تنظيف مرفقات المرتجعات كان يجري مسحًا كاملًا لـJSON. أُضيف فهرس GIN على `attachments::jsonb` عبر migration مستقلة، تدعم إعادة المحاولة بعد فهرس CONCURRENTLY غير صالح، ولها rollback.
6. migration إنشاء `media` كانت بلا `down()`، مما يمنع إعادة البناء بعد rollback كامل. أُضيف حذف الجدول عند التراجع، وأُعيدت دورة المهاجرات كاملة.
7. أُصلحت تجهيزات اختبارات الواجهة لتوفير بيئة المتصفح حيث يلزم، وتحميل استيرادات TypeScript الجديدة. بقي منع `setAuthToken` على الخادم مفعّلًا، مع اختبار عزل عميلين متزامنين في SSR.

## نتائج الحجم والأداء

البيانات مصطنعة على PostgreSQL 16 محلية ومعزولة، وليست قياسًا لزمن HTTP في الإنتاج أو SLA. الفهارس بُنيت ثم أُجري ANALYZE. الجدول المؤقت حُذف بعد القياس.

| التجربة | الحجم | النتيجة |
|---|---|---|
| قائمة الإشعارات، أول 20 | 6,000,000 صف / 2551 MB مع الفهارس | `notifications_recipient_created_idx`، زمن التنفيذ 0.245 ms |
| عد غير المقروء لمستلم | الحجم نفسه | `notifications_unread_recipient_created_idx`، زمن التنفيذ 0.318 ms |
| اختيار دفعة تنظيف 1000 صف | الحجم نفسه، حد 14 يومًا لإيجاد صفوف مرشحة | `notifications_created_at_idx`، زمن التنفيذ 0.678 ms |
| بحث 500 مسار JSON قبل الفهرس | 100,000 صف | Seq Scan، 75,060.485 ms؛ يتجاوز مهلة 30 ثانية |
| البحث نفسه بعد GIN | الحجم والمرشحات نفسيهما | Bitmap Heap Scan باستخدام الفهرس الجديد، 202.000 ms |

القياس الأخير يقيس بحث مراجع JSON في دفعة التنظيف، ولا يشمل زمن سرد R2 أو حذف الملفات عبر الشبكة. تشغيل `attachments-scale.sql` مع `-v use_index=false` يعيد قياس ما قبل الفهرس؛ الافتراضي يستخدم الفهرس.

## ملاحظات تشغيلية وحدود التحقق

- مسارات الموردين والمشتريات متوقفة عمدًا بـ410 في `ManufacturingBusiness`. اختبارات القواعد التاريخية تتجاوز هذه البوابة وحدها باستخدام أسلوب المستودع، وتبقي المصادقة والصلاحيات والتحقق. لم يُلغَ إيقاف المسارات.
- الرصيد المخزني السالب ممنوع أصلًا بقيد `stock_levels_valid_balances`. لا حاجة لتغيير سياسة التكلفة للسماح برصيد سالب.
- نافذة الإرجاع الحالية تُقاس من لحظة التسليم بالضبط: الحد نفسه مقبول، وبعده بثانية مرفوض. هذه الاختبارات تثبّت السلوك الحالي.
- اختبار Redis المعزول أثبت رفض الكتابة بـOOM عند الامتلاء، وبقاء قفل أمني وعدم إخلاء مفاتيح. وصول التنبيه من Prometheus وسلوك HTTP أثناء امتلاء Redis يحتاجان بيئة تشغيل متكاملة.
- لم يُشغّل `fault-check.mjs` على staging، أو استرجاع النسخ الاحتياطية الفعلية، أو اختبار مرور المهل عبر PgBouncer حي. هذه تتطلب بيئة وخدمات مناسبة؛ لا تُعتبر ناجحة اعتمادًا على اختبارات PostgreSQL المباشرة.
- الرفع والتوقيع والتنظيف اختُبرت بأقراص وهمية ومحلية، دون الاتصال بحساب R2 الحقيقي.
- عند النشر يلزم تطبيق migration الجديدة `2026_10_29_000013_index_private_return_attachments.php` عبر مسار المهاجرات المعتاد. تغييرات الخدمة وحدها لا تنشئ فهرس GIN.
