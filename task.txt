خطة تنفيذ Load Balancing وHigh Availability لمنصة الفريد (bags-platform)
مقدمة: إزاي الـ Load Balancer يرفع سعر السيستم فعلاً
قريت الكود. المشتري الفاهم مش هيدفع أكتر لمجرد إن فيه ملف إعدادات HAProxy. اللي هيدفع فيه هو دليل مكتوب بالأرقام إن السيستم بيتحمل ضغط حقيقي وما بيقعش لما سيرفر يقع. عشان كده الخطة بتنتهي بحاجتين: تقرير اختبار حمل فيه مقارنة بين سيرفر واحد وتلات سيرفرات، واختبار فشل بنطفي فيه سيرفر والسيستم شغال. دول اللي هتعرضهم وقت البيع.

الأخبار الكويسة: الكود جاهز تقريباً للتوسع:

الـ auth معمول بـ Bearer tokens، وsupports_credentials في CORS قيمته false، فمش محتاج sticky sessions.
فيه OperationIdempotencyService.
الـ exception handler بيرجّع 503 ومعاه Retry-After في حالة الـ deadlock.
فيه health check جاهز على /up.
الـ services معمول لها scoped.
الـ production بيرفض TRUSTED_PROXIES لو قيمتها wildcard.
الأدوات كلها مجانية ومفتوحة المصدر: HAProxy وNginx وPHP-FPM وPgBouncer وRedis Sentinel وKeepalived وPrometheus وGrafana وLoki وk6 وDocker. التكلفة الوحيدة سيرفرات لو حبيت تشغّل على بيئة حقيقية. للديمو كفاية جهاز Linux واحد بـ 16GB رام.

1.2 Middleware للـ Request ID
اعمل ملف app/Http/Middleware/AssignRequestId.php:

Copy<?php

declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;
use Illuminate\Support\Str;
use Symfony\Component\HttpFoundation\Response;

final class AssignRequestId
{
    public function handle(Request $request, Closure $next): Response
    {
        $id = $request->headers->get('X-Request-ID');
        if (! is_string($id) || ! preg_match('/\A[A-Za-z0-9._:-]{8,128}\z/', $id)) {
            $id = (string) Str::uuid();
        }

        Log::withContext([
            'request_id' => $id,
            'node' => gethostname(),
            'client_ip' => $request->ip(),
        ]);

        $response = $next($request);
        $response->headers->set('X-Request-ID', $id);

        if (config('app.expose_node_header')) {
            $response->headers->set('X-Served-By', (string) gethostname());
        }

        return $response;
    }
}
Copy
سجّله في bootstrap/app.php جوه withMiddleware: $middleware->prepend(\App\Http\Middleware\AssignRequestId::class);
ضيف في config/app.php: 'expose_node_header' => (bool) env('APP_EXPOSE_NODE_HEADER', false), وخليه true في الديمو بس، عشان تبيّن للمشتري إن الطلبات بتتوزع على السيرفرات.

1.4 Readiness Health Check
/up بيقول بس إن PHP شغال. محتاجين endpoint بيتأكد من الداتابيز وRedis كمان. اعمل app/Http/Controllers/HealthReadyController.php:

Copy<?php

declare(strict_types=1);

namespace App\Http\Controllers;

use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Redis;
use Throwable;

final class HealthReadyController
{
    public function __invoke(): JsonResponse
    {
        $checks = [];

        try { DB::select('select 1'); $checks['db'] = 'ok'; }
        catch (Throwable) { $checks['db'] = 'fail'; }

        try { Redis::connection('default')->ping(); $checks['redis'] = 'ok'; }
        catch (Throwable) { $checks['redis'] = 'fail'; }

        $checks['storage'] = is_writable(storage_path('framework')) ? 'ok' : 'fail';

        $ok = ! in_array('fail', $checks, true);

        return response()
            ->json(['status' => $ok ? 'ok' : 'fail', 'checks' => $checks], $ok ? 200 : 503)
            ->header('Cache-Control', 'no-store');
    }
}
Copy
سجّل الـ route في bootstrap/app.php جوه callback الـ then:، ومن غير web middleware عشان ما يفتحش session ويكتب في الداتابيز مع كل health check:

2.4 حساب PHP-FPM workers
المعادلة: pm.max_children = (رام السيرفر المتاحة لـ PHP) ÷ (متوسط رام الـ process).
إزاي تقيس متوسط الرام: تحت ضغط شغّل ps -ylC php-fpm --sort:rss وخد المتوسط. غالباً هيطلع بين 60 و90MB.
مثال: سيرفر 4GB، فيه 3GB متاحة لـ PHP، يبقى 3000 ÷ 80 ≈ 36. قرّبها لـ 32.
استخدم pm = static في الـ production.

المرحلة 3: طبقة HAProxy — 3 إلى 4 أيام
استخدم haproxy:3.0 (نسخة LTS مجانية). اعمل infrastructure/haproxy/haproxy.cfg:

Copyglobal
    log stdout format raw local0
    maxconn 50000
    stats socket /var/run/haproxy/admin.sock mode 660 level admin expose-fd listeners
    ssl-default-bind-options ssl-min-ver TLSv1.2

defaults
    mode http
    log global
    option httplog
    option dontlognull
    option http-keep-alive
    option redispatch
    retries 2
    retry-on conn-failure empty-response
    timeout connect 5s
    timeout client 30s
    timeout server 60s
    timeout http-request 10s
    timeout http-keep-alive 5s
    timeout queue 20s

frontend fe_public
    bind :80
    bind :443 ssl crt /etc/haproxy/certs/ alpn h2,http/1.1
    http-request redirect scheme https code 301 unless { ssl_fc }

    # Request ID
    unique-id-format %[uuid()]
    unique-id-header X-Request-ID

    # امسح أي X-Forwarded-For جاي من العميل (منع تزوير IP) وحط الحقيقي
    http-request del-header X-Forwarded-For
    option forwardfor
    http-request set-header X-Forwarded-Proto https if { ssl_fc }
    http-request set-header X-Forwarded-Port %[dst_port]

    # ما تسمحش بإعادة محاولة أي طلب بيغيّر بيانات
    http-request disable-l7-retry unless METH_GET || METH_HEAD

    # health endpoints داخلية فقط
    http-request deny deny_status 404 if { path_beg /health } || { path /up }

    # حد أقصى لحجم الطلب 25MB
    http-request deny deny_status 413 if { req.hdr_val(content-length) gt 26214400 }

    # Edge rate limiting (طبقة أولى قبل Laravel)
    stick-table type ipv6 size 1m expire 60s store http_req_rate(10s),conn_cur
    acl whitelisted src -f /etc/haproxy/whitelist.lst
    http-request track-sc0 src unless whitelisted
    http-request deny deny_status 429 if { sc_http_req_rate(0) gt 300 }
    http-request deny deny_status 429 if { sc_conn_cur(0) gt 100 }

    # Routing بالدومين
    acl host_api   hdr(host),field(1,:) -i api.alfarid.example
    acl host_admin hdr(host),field(1,:) -i admin.alfarid.example
    acl host_pos   hdr(host),field(1,:) -i pos.alfarid.example

    use_backend be_api        if host_api
    use_backend be_backoffice if host_admin
    use_backend be_pos        if host_pos

    option httpchk

    http-check expect status 200
    default-server check inter 3s fall 3 rise 2 slowstart 20s maxconn 32
    server app1 app1:8080
    server app2 app2:8080
    server app3 app3:8080

شرح القرارات المهمة (اكتبها في التوثيق، لأنها اللي هتبيّن للمشتري إن الشغل احترافي):

maxconn 32 لكل سيرفر: بيساوي pm.max_children. HAProxy بيحجز الطلبات الزيادة في طابور بدل ما يغرق PHP-FPM، وده بيمنع انهيار السيرفر تحت الضغط.
leastconn: بيبعت الطلب للسيرفر الأقل انشغالاً. مناسب لـ API فيه طلبات مدتها مختلفة جداً، زي checkout مقابل catalog.
be_api_slow: التقارير وتصدير PDF وExcel ليها timeout أطول وعدد اتصالات محدود، عشان ما تاخدش كل الـ workers وتوقف الـ checkout.
disable-l7-retry: HAProxy ما بيعيدش أي POST أبداً، فمستحيل طلب أوردر يتكرر. ده مكمّل للـ Idempotency service ولسلوك الـ exception handler اللي بيرجّع 409 على عمليات الكتابة.
slowstart 20s: السيرفر الراجع من deploy بياخد الحمل بالتدريج لحد ما الـ OPcache يسخن.
حد الـ edge (300 طلب في 10 ثواني): أعلى من حدود Laravel. الهدف هنا صد الهجمات قبل ما توصل PHP. فروع الـ POS اللي وراها NAT حطها في whitelist.lst.
TLS مجاني: استخدم certbot مع Let's Encrypt، وادمج الـ fullchain والـ key في ملف .pem واحد في /etc/haproxy/certs/، واعمل cron للتجديد ثم kill -USR2 لـ HAProxy عشان يعيد التحميل من غير ما يقطع اتصالات. لو حطيت Cloudflare (الخطة المجانية) قدام HAProxy، هتحتاج تاخد IP العميل من CF-Connecting-IP بس لما الطلب يكون جاي من نطاقات Cloudflare الرسمية. ده تعديل منفصل.

4.1 PgBouncer (Connection Pooling)
ليه: 3 سيرفرات × 32 worker = 96 اتصال، وفوقهم الـ workers والـ scheduler. PostgreSQL بيتعب مع الاتصالات الكتير. PgBouncer بيخلّي كل دول يشتغلوا على حوالي 40 اتصال حقيقي.

اعمل infrastructure/pgbouncer/pgbouncer.ini (محتاج نسخة 1.21 أو أحدث):

Copy[databases]
alfarid = host=postgres port=5432 dbname=alfarid

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 40
reserve_pool_size = 10
max_prepared_statements = 200
client_tls_sslmode = require
client_tls_key_file = /etc/pgbouncer/tls/server.key
client_tls_cert_file = /etc/pgbouncer/tls/server.crt
server_tls_sslmode = require
تحذيرات مهمة جداً (لازم تنفذها بالترتيب):

TLS إجباري: AppServiceProvider بيرفض أي DB_SSLMODE أضعف من require في الـ production، فـ PgBouncer لازم يدعم TLS من ناحية العميل. اعمل شهادة self-signed مجانية:
Copyopenssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=pgbouncer" -keyout server.key -out server.crt
Advisory locks: التوثيق بيقول إن الكود بيستخدم advisory locks. ابحث:
Copygrep -rn "pg_advisory_lock\|pg_try_advisory_lock\|pg_advisory_xact_lock\|SET \|set_config" app/ database/
pg_advisory_xact_lock مرتبط بالـ transaction، وده آمن.
pg_advisory_lock من غير xact مرتبط بالـ session، وده هيتكسر في transaction mode. لو لقيته يا إما تحوّله لـ xact، يا إما تخلي pool_mode = session، ويا إما تعمل connection منفصلة اسمها pgsql_direct تتصل بـ Postgres على طول وتستخدمها للحتة دي بس.
SET LOCAL آمن. لكن SET من غير LOCAL مش آمن.
Laravel بينفذ set names 'utf8' وset search_path to public أول ما يفتح الاتصال. دول مش هيعملوا مشكلة لأنهم نفس القيم الافتراضية للسيرفر. اتأكد إن الداتابيز encoding بتاعها UTF8.
في .env: DB_HOST=pgbouncer وDB_PORT=6432. الـ migrations شغّلها على Postgres مباشرة مش من خلال PgBouncer.
شغّل الـ test suite كلها على PgBouncer قبل ما تكمل.
4.2 Redis High Availability
الإعداد: Redis master وreplica و3 Sentinels. الـ Sentinels بيرقّوا الـ replica لـ master لو الـ master وقع.

phpredis مش بيتكلم مع Sentinel بشكل مباشر. الحل المجاني المعروف إننا نحط haproxy-data قدام Redis، وده بيبعت الاتصالات للـ master الحالي بس. اعمل infrastructure/haproxy/haproxy-data.cfg:

Copydefaults
    mode tcp
    timeout connect 3s
    timeout client 1h
    timeout server 1h

frontend fe_redis
    bind :6379
    default_backend be_redis

backend be_redis
    option tcp-check
    tcp-check connect
    tcp-check send AUTH\ ${REDIS_PASSWORD}\r\n
    tcp-check expect string +OK
    tcp-check send PING\r\n
    tcp-check expect string +PONG
    tcp-check send info\ replication\r\n
    tcp-check expect string role:master
    tcp-check send QUIT\r\n
    tcp-check expect string +OK
    server redis1 redis1:6379 check inter 1s
    server redis2 redis2:6379 check inter 1s
إعدادات Redis: requirepass وmasterauth وappendonly yes.
إعدادات Sentinel: sentinel monitor mymaster redis1 6379 2 مع down-after-milliseconds 5000.
في .env: REDIS_HOST=haproxy-data وREDIS_PASSWORD=.... ما تسيبهاش null زي ما هي في .env.production.example الحالي.

المرحلة 6: High Availability للـ Load Balancer نفسه — يوم واحد
Keepalived بيعمل IP عائم (VIP) بين HAProxy 1 وHAProxy 2. لو واحد وقع، التاني ياخد الـ IP في أقل من 3 ثواني.

Copyvrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"
    interval 2
    weight -20
}

vrrp_instance VI_1 {
    state MASTER            # BACKUP على السيرفر التاني
    interface eth0
    virtual_router_id 51
    priority 110            # 100 على السيرفر التاني
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass CHANGE_ME
    }
    virtual_ipaddress {
        192.168.1.100/24
    }
    track_script {
        chk_haproxy
    }
}
ملاحظة صريحة: Keepalived محتاج شبكة L2 مشتركة، زي Docker على Linux أو LAN أو VPS provider بيدعم floating IP. على الكلاود العادي الـ floating IP غالباً بفلوس قليلة. للديمو المجاني، شغّله في Docker على Linux بصلاحية NET_ADMIN.

شروط القبول: docker stop haproxy1 أثناء اختبار الحمل، والطلبات تكمل على الـ VIP.

المرحلة 8: Deploy من غير توقف (Zero-Downtime) — يومين
اعمل infrastructure/scripts/rolling-deploy.sh:

Copy#!/usr/bin/env bash
set -euo pipefail
SOCK=/var/run/haproxy/admin.sock
NODES=(app1 app2 app3)

hap() {
  for h in haproxy1 haproxy2; do
    docker compose exec -T "$h" sh -c "echo '$1' | socat stdio $SOCK"
  done
}

# 1) build الـ image الجديدة
docker compose build app1

# 2) migrations مرة واحدة بس (لازم تكون backward-compatible)
docker compose run --rm app1 php artisan migrate --force

# 3) rolling على كل سيرفر
for n in "${NODES[@]}"; do
  echo ">> draining $n"
  hap "set server be_api/$n state drain"
  sleep 20   # استنى الطلبات الجارية تخلص

  docker compose up -d --no-deps --force-recreate "$n"

  echo ">> waiting for $n to be ready"
  for i in $(seq 1 60); do
    if docker compose exec -T "$n" curl -fsS http://localhost:8080/health/ready >/dev/null; then
      break
    fi
    sleep 2
    [ "$i" = 60 ] && { echo "FAILED: $n"; exit 1; }
  done

  hap "set server be_api/$n state ready"
done

# 4) workers
docker compose up -d --no-deps --force-recreate worker media-worker scheduler
docker compose exec -T app1 php artisan queue:restart
Copy
قاعدة الـ migrations (اكتبها في الـ runbook): أي migration لازم يكون متوافق مع الكود القديم، لأن أثناء الـ deploy فيه سيرفرات شغالة بالكود القديم.

إضافة عمود تتم على خطوتين: deploy فيه العمود nullable، وبعدين deploy تاني يستخدمه.
حذف عمود يتم على خطوتين: deploy يبطّل يستخدمه، وبعدين deploy يحذفه.
الالتزام ده موجود أصلاً في توثيقك، زي ترتيب migrations 000004 لـ 000006.

شروط القبول: deploy كامل أثناء اختبار حمل k6، بنسبة أخطاء 0%.

9.1 سكريبت k6
اعمل infrastructure/k6/store-load.js:

Copyimport http from 'k6/http';
import { check, sleep } from 'k6';

const BASE = __ENV.BASE_URL;
const SLUGS = JSON.parse(open('./slugs.json'));

export const options = {
  scenarios: {
    browse: {
      executor: 'ramping-vus',
      stages: [
        { duration: '2m', target: 200 },
        { duration: '5m', target: 500 },
        { duration: '2m', target: 0 },
      ],
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<800'],
  },
};

function fakeIp() {
  return `10.${__VU % 250}.${Math.floor(Math.random() * 250)}.${(__ITER % 250) + 1}`;
}

export default function () {
  const h = { headers: { 'X-Forwarded-For': fakeIp(), Accept: 'application/json' } };
  check(http.get(`${BASE}/api/v1/store/home`, h), { home: (r) => r.status === 200 });
  check(http.get(`${BASE}/api/v1/store/products?sort=newest`, h), { list: (r) => r.status === 200 });
  const s = SLUGS[Math.floor(Math.random() * SLUGS.length)];
  check(http.get(`${BASE}/api/v1/store/products/${s}`, h), { pdp: (r) => r.status === 200 });
  sleep(1);
}
Copy
الـ IP العشوائي: k6 بيشتغل من جوه الشبكة الداخلية على frontend الـ :8081 (اللي ما بيمسحش X-Forwarded-For)، فكل مستخدم وهمي بيظهر لـ Laravel بـ IP مختلف، والـ rate limiters تشتغل بشكل واقعي. لازم تضيف IP الـ k6 container في TRUSTED_PROXIES في بيئة الاختبار بس.

#	الاختبار	المتوقع

مراحل اختيارية (بعد ما الأساسي يخلص ويستقر)
A. Micro-cache للكتالوج (مكسب أداء كبير)
كاش لمدة 10 ثواني في Nginx على كل سيرفر، لطلبات GET /api/v1/store/{home,categories,products...} اللي مش معاها Authorization ولا X-Cart-Session.

قبل ما تنفّذ:

اتأكد إن الـ response ما بيختلفش حسب أي header تاني، زي اللغة أو الفرع.
ما تكيّشش أي response فيه Set-Cookie أو Cache-Control: private. الـ ProtectStorefrontCaching الموجود عندك بيحط private, no-store للمستخدم المسجل، فاحترمه.
خد موافقة صاحب البيزنس إن حالة المخزون ممكن تتأخر 10 ثواني.
B. Laravel Octane (مع FrankenPHP)
ممكن يضاعف الأداء 2 لـ 4 مرات. الكود متجهز جزئياً، لأن الـ services معمول لها scoped بالتحديد "لتجنب تسريب state في Octane". لكن الخطر عالي: أي static property أو singleton فيه state ممكن يسرّب بيانات عميل لعميل تاني.

شروط التنفيذ: test suite كاملة، ومراجعة كل static في app/، واختبار حمل بمستخدمين مختلفين مع التأكد إن مفيش بيانات بتتخلط. لو أي شك، ما تنفذوش.

C. Read Replica للتقارير
Postgres streaming replication (مجاني)، واعمل connection منفصلة اسمها pgsql_reports تستخدمها endpoints التقارير بس. ما تعملش read/write split عام، لأن الكود معتمد بشكل كبير على lockForUpdate، والقراءة من replica متأخرة ممكن تعمل أخطاء في المخزون.
